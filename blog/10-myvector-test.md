# "다 됩니다"를 증명하는 법: MyVector 테스트 만들기

## 궁금했던 것

MyVector를 처음 보는 사람이 "이거 제대로 동작해?"라고 물으면 뭐라고 답해야 할까?

처음 내 답:

> 복사 생성도 되고, 이동 생성 되고, 복사 대입, 이동 대입 등 다 됩니다. 알아서 해제도 메모리 누수 없이 해 줘요라고 말하면 되나?

기능 목록은 맞다. 하지만 "된다"고 말하는 것과 증명하는 것은 다르다. 증명하려면 각 기능을 **상황**과 **기대**로 바꿔야 한다.

## 실험 설계

### 상황과 기대로 바꾸기

이동 대입을 직접 바꿔 봤다.

```
상황  : a에 1, 2, 3을 넣고 MyVector b; b = std::move(a);
기대  : b.size()는 3, b[0~2]는 1, 2, 3, a.size()는 0
```

이걸 assert로 옮기면 테스트가 된다.

```cpp
void TestMoveAssign()
{
	MyVector<int> a;
	a.push_back(1); a.push_back(2); a.push_back(3);
	MyVector<int> b;
	b = std::move(a);

	assert(b.size() == 3);
	assert(b[0] == 1);
	assert(b[1] == 2);
	assert(b[2] == 3);
	assert(a.size() == 0);
}
```

> 약간 실수가 있던 게 함수를 메인 함수 아래 써 가지고 순간 정의가 없다고 떴었어.

### 테스트의 테스트: 일부러 버그 넣기

테스트가 진짜로 버그를 잡는지 확인하려고, 지금까지 실제로 났던 버그를 일부러 다시 넣은 MyVector로 돌렸다.

## 결과

### 문제 1: 값만 확인하면 얕은 복사를 못 잡는다

복사 생성 테스트에서 값과 size만 확인했더니, 복사 생성자를 얕은 복사로 망가뜨려도 assert는 전부 통과하고 프로그램 끝에서 이중 해제로 죽었다. 얕은 복사여도 같은 판을 보니까 값은 똑같기 때문이다.

복사본을 바꾼 다음 원본이 그대로인지 확인해야 한다.

```cpp
c[0] = 100;
assert(d[0] == 1);
```

### 문제 2: 테스트끼리 엉킨다

> c[0] = 100을 넣으니까 순간 f[0] == 1에서 assert가 나더라. 이제 값이 바뀌었으니까.

복사 대입 테스트가 앞 테스트의 c를 이어 쓰고 있었다. 테스트를 기능별 함수 네 개로 나누고, 각자 자기 벡터를 새로 만들게 했다.

> 또 f[0] = 100으로 까먹고 빌드하니까 에러 나더라. 그래그래, 유용하게 몸으로 맞고 있네.

### 문제 3: assert는 Release에서 꺼진다

같은 버그 버전을 Release로 돌리니 통과해 버렸다. assert는 Release 빌드에서 사라진다. 성능은 Release로, 테스트는 Debug로.

### 최종 검증

```
진짜 코드                → 통과
복사 생성자 얕은 복사    → Assertion failed: d[0] == 1, line 27
이동 대입 size 안 받음   → Assertion failed: b.size() == 3, line 72
복사 대입 얕은 복사      → Assertion failed: d[0] == 1, line 43
```

버그 세 개를 모두 정확한 줄에서 잡는다.

## 왜 그런가

- 테스트는 "버그가 있으면 실패하는 확인"이어야 한다. 정상일 때 통과하는 것만으로는 부족하다.
- 얕은 복사는 값이 같아 보여서, 한쪽을 바꾼 뒤 다른 쪽을 확인해야 드러난다.
- 테스트는 서로 독립이어야 한다. 앞 테스트가 바꾼 값에 뒤 테스트가 기대면, 상관없는 테스트가 같이 깨진다.
- 테스트가 버그를 잡는지는, 일부러 버그를 넣어 보면 확인할 수 있다.

## 정리

사실 아직도 부족하다고 생각은 한다. 그래도 전처럼 "아마 그렇게 하면 되지 않을까?"에서, 해 보는 걸로 성장한 것 같다. 물론 아직도 실전에서 이런 게 먹힐지 두렵지만, 그래도 꾸준히 하다 보면 나아지지 않을까 생각한다.
